# API authorization audit — 2026-11-17

Black-box probe of the running Docker stack (`127.0.0.1:8000`) plus static reading
of the id-taking controllers under `Backend/src/Controller/` and their managers.
No product code was modified: `Backend/` is read-only for this side of the team.
Test artifacts written during the probe (one `chat_messages` row, the
`CHAT_MESSAGE` notification it produced) were deleted afterwards; the demo seed
is back to its committed state.

Every finding below is **Fact**: reproduced with the commands in
[Reproduction](#reproduction), or read at the cited `path:line`. Severity is a
judgment, marked as such.

Stack at probe time: `backend-backend-1` up on `0.0.0.0:8000`, `backend-database-1`
healthy, six demo accounts from `docker/seed-demo.sql` (password `demo1234`).
Reachable on the host as `127.0.0.1:8000`, **not** as `localhost:8000` (connection
refused; the commands in `docs/setup.md` use `localhost`).

---

## A1 — Any authenticated user reads any chat, by `agreementId`

**Fact.** `GET /api/chats/agreement/1` with the token of `sara.mancini` (`user_id 3`)
answers `200 {"chatId":1,"messages":[]}`. `chat_participants` holds exactly two rows
for chat 1: `user_id 8` and `user_id 10`. Sara is not one of them.

Cause: `ChatController::getChatAndHistoryByAgreementId`
(`Backend/src/Controller/ChatController.php:27`) checks only that a user is
authenticated, then calls `ChatManager::getOrCreateChat($agreementId)`
(`ChatManager.php:46`), which resolves the chat by agreement and returns it with
no participant check. `getChatHistory($chat)` likewise takes the chat, not the
viewer.

Worse than a read: `getOrCreateChat` **creates** the chat and its participants
when the agreement has none, so a non-participant can trigger that write path too.

**Impact (judgment).** Message contents of every conversation in the system are
readable by any logged-in account that walks `agreementId` (integers). Today the
seed has no messages, so the leak is invisible — it appears with the first real
message. The frontend consumes exactly this call
(`Frontend/src/api/areas/chat.js:97`), so the endpoint cannot simply be removed.

## A2 — Any authenticated user writes into any chat

**Fact.** `POST /api/chats/send-message/1` with Sara's token and
`{"message":"test authz - non partecipante"}` answered
`200 {"success":{"code":200,"message":"Message sent successfully"}}`.
`chat_messages` then held `id 1, chat_id 1, user_id 3` with that text, and
`notifications` gained `CHAT_MESSAGE / "Nuovo messaggio da: sara.mancini"` for
`user_id 8` — a stranger's message inside a conversation user 8 is part of.

Cause: `ChatManager::sendMessage` (`ChatManager.php:78`) loads the chat by id,
validates the message, persists it, then notifies
`getOtherParticipant($chat, $user)`. The sender's membership in `$chat` is never
verified.

**Impact (judgment).** Highest of the four: the write path is silent for the
sender and loud for the victim (an in-app notification plus a message row in their
chat), so it needs no guessing to be noticed. Combined with A1 it makes every
conversation readable and writable.

## A3 — A missing agreement returns `500` with the exception text

**Fact.** `GET /api/chats/agreement/999` (any valid token) answers
`500` with a Symfony error page:
`Call to a member function getAgreementProposals() on null`.

Cause: `getOrCreateChat` calls
`$this->agreementManager->getAgreementById($agreementId)` and dereferences it
without a null check (`ChatManager.php:51-52`). The `catch (\Exception)` block in
the controller does not catch it because the failure is an `Error`, not an
`Exception`. The generic branch that *does* run (`ChatController.php:44`) returns
`'Internal server error ' . $e->getMessage()`, so even caught exceptions leak
internals into the body.

**Impact (judgment).** Low on its own, high as a signal: in dev the page carries
file paths and a stack trace, and the message-suffix pattern would echo driver and
entity details in production too.

## A4 — `POST /api/cancel-queue/{id}` on another account's queue answers `200`

**Fact.** Sara cancelling queue 1 (Giulia's) answered `200` and changed nothing:
the queue is still `OPEN` in `service_queues` and still listed by
`GET /get-queues` for Giulia. Already recorded as `backend-gaps.md` G21.

Not a privilege escalation — a confirmation that the documented "always `200`,
even on a no-op" behaviour is real and that the app reads it as success
(«Coda annullata»). No new request to the backend here; G21 covers the fix.

## A5 — `POST /auth/login` has no rate limit

**Fact.** Fifteen consecutive failed logins for `sara.mancini` answered `401`
fifteen times with no `429`, no delay and no lockout; the correct password
succeeded immediately afterwards (`200`). No `rate_limiter` key exists in
`Backend/config/**`: the only match for the string in the tree is the framework
stub `config/reference.php`.

Not exploitable on a demo seed with published passwords, but the app is heading
for a real deployment and `AGENTS.md` lists rate limiting on public endpoints as
a pre-commit requirement.

## A6 — `POST /send-agreement-details` has no participant check and crashes on a stranger

**Fact, from source — not reproduced.** `AgreementManager::sendAgreementDetails`
(`Backend/src/Manager/AgreementManager.php:149`) loads the agreement by id and
accepts any `ACCEPTED` one, with no `isParticipant` call — unlike
`cancelAgreement` (`:181`) and `acceptAgreementDetails` (`:207`), which both call
it. Two consequences:

1. A stranger can reach the details row of the two real participants only through
   `getAgreementDetailsByUser($agreement->getId(), $user)` (`:163`), which *is*
   scoped by user (`Repository/AgreementDetailsRepository.php:39`), so it returns
   `null` for the stranger and `:164` dereferences it: `500`, not `404`.
2. Any authenticated account can drive any `ACCEPTED` agreement to a server error
   by guessing the id — the same failure class as A3, one endpoint further in.

Not reproduced live because the seed's only agreement is `PENDING` (`agreements`
row 1); reaching `ACCEPTED` needs the credentials of a third participant.

## What held

Probed with the token of `sara.mancini` (`user_id 3`) against rows owned by other
accounts; every call below answered `404`/`403` and left the data unchanged
(checked in `services` and `users` afterwards):

| Call | Result |
| --- | --- |
| `PATCH /notifications/1/read` (owner `user_id 8`) | `404` |
| `GET /staff/operations/1`, `POST /users/2/promote`, `PATCH /users/2/status` | `403`, `404`, `404` |
| `PATCH /offers/1` and `PATCH /requests/2` (owner `user_id 1`) | `404` |
| `POST /accept-agreement-details/1`, `POST /send-agreement-response` | `404` |
| `401` without a token, `401` with a malformed token | both correct |
| `GET /get-agreements`, `GET /notifications` | scoped to the caller |
| `GET /chats/check-new-messages/{id}` | scoped to the caller's chats |
| login error for unknown user vs wrong password | identical string, no enumeration |
| `POST /auth/register` with a 3-character password | `400` (`AuthController.php:126` requires 8) |

By design and not a defect: `GET /users/{id}/services` answers `200` for any
active owner (`docs/api.md`).

The two chat endpoints (A1, A2) are the exception that proves the rule: every
newer controller resolves the row *through* the viewer (`findOwned`,
`findOneBy([... 'user' => $user])`, `isParticipant`), while `ChatManager` loads
by id and never looks at who asked.

## Proposals for the backend maintainer

Not applied — `Backend/` is read-only here. In priority order:

1. `ChatManager::getOrCreateChat` takes the viewer and rejects (or returns `404`
   for) an agreement the viewer has no proposal on. `getAgreementProposals()`
   already carries the users, so the check needs no new query.
2. `ChatManager::sendMessage` asserts `$user` is in `chat_participants` for
   `$chat` before `persist`.
3. Null check on `getAgreementById` in `getOrCreateChat` → `404`, instead of
   dereferencing null.
4. `ChatController` stops appending `$e->getMessage()` to the body, and catches
   `\Throwable` where it means to catch everything.
5. `AgreementManager::sendAgreementDetails` calls `isParticipant` first, and null
   checks the details row it dereferences (`:164`).
6. A `login` rate limiter in `config/packages/rate_limiter.yaml` plus the
   `#[RateLimiter]`-style guard on `AuthController::login`. Out of frontend scope,
   listed because it is the only finding here that a real deployment cannot ship
   with.

## Reproduction

```bash
B=http://127.0.0.1:8000/api
tok() { curl -s -X POST $B/auth/login -H 'Content-Type: application/json' \
  -d "{\"username\":\"$1\",\"password\":\"demo1234\"}" | jq -r .token; }
SARA=$(tok sara.mancini)

# A1 — read a conversation she is not in (chat 1 belongs to users 8 and 10)
curl -s $B/chats/agreement/1 -H "Authorization: Bearer $SARA"

# A2 — write into it (creates a row and a notification for the victim)
curl -s -X POST $B/chats/send-message/1 -H "Authorization: Bearer $SARA" \
  -H 'Content-Type: application/json' -d '{"message":"test"}'

# A3 — unknown agreement
curl -s $B/chats/agreement/999 -H "Authorization: Bearer $SARA"

# A5 — no rate limit: 15 rejections, then a normal login
for i in $(seq 1 15); do
  curl -s -o /dev/null -w '%{http_code} ' -X POST $B/auth/login \
    -H 'Content-Type: application/json' -d '{"username":"sara.mancini","password":"nope"}'
done; echo
```
