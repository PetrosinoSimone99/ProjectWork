# UX / UI / design critique — 2026-11-13

Third full read of `Frontend/`, and the second one taken against rendered
screens. It is written to be worked from, not read once: every finding carries
its evidence, why it matters, and the smallest fix that closes it.

**Method: dual-agent.** Two isolated read-only assessments, run in parallel
without seeing each other:

| Lane | Scope | Output |
| --- | --- | --- |
| **A** — design review (`reviewer`) | the 2026-11-12 captures plus the code that draws them: specificity, heuristics, cognitive load, emotional journey, composition | heuristics 27/40, 3 × P1, 2 × P2, 10 minor |
| **B** — deterministic + technical (`reviewer`) | contrast recomputed from `theme/tokens.js`, token bypasses, touch targets, a11y attributes, focus management, state matrix, responsive rules, source hygiene | 0 contrast failures, 4 sub-44pt targets, 3 one-channel live regions, 9 files > 400 lines |
| **parent** — browser leg | `impeccable detect`, live DOM measurement (headings, targets, `document.title`, column geometry at 1920), screenshot reading | detector clean, 3 measured defects |

The browser leg ran in the parent because the sub-agents do not inherit the
browser MCP in this harness; that is declared here rather than hidden.

**Target:** `Frontend/src` (slug `frontend-src-app`). **Surface mode:**
**Operate** — people browse a catalog, publish an entry, send a proposal,
moderate reports. Brand lives in precise details, not in expression.

**Tree read:** `c3442ba` (`refactor: carry the web refresh in the chrome bar`),
working tree clean under `Frontend/`. The captures in
[`screens-2026-11-12/`](screens-2026-11-12/) were taken after that commit with
the Symfony backend up, so they are the visual evidence of record for this
exact tree.

**Environment limits.** The Docker stack was **not** running in this session and
Docker Desktop could not be started, so no authenticated screen could be
re-rendered live. Everything measured live is on the two unauthenticated routes
(`/login`, `/register`); every other claim is either read from source or read off
the 2026-11-12 captures. Native iOS/Android were not rendered (no simulator).
See §9 for the full list of what this critique did **not** verify.

## 2. Design specificity

**Grounded where the data model is, generic where the shell is.**

Specific to this product, structurally — not just in copy:

- **The card headline is the person's sentence and nothing competes with it.**
  `ServiceCard.jsx:100-110` renders `servizio.descrizione` at `heading` (19/700,
  three lines) and demotes it out of the heading role; the category is an 11 px
  pill in the meta strip. No name, no price, no rating — the card could not exist
  in a marketplace where a service is a SKU.
- **The detail sheet chooses what a person needs to judge a human**, and refuses
  to fabricate: "Cosa offre e cerca — Non disponibile per ora: di questa persona
  vediamo la scheda e il servizio che ti interessa"
  (`mobile-390-service-detail.png`). A backend gap rendered as honest layout.
- **The blind proposal is stated at the point of commitment**, in one line
  attached to the button: "La proposta è alla cieca, non vincolante: la decide
  l'altra persona" (`ServiceDetailModal.jsx:120`).
- **The one-entry ceiling is drawn honestly**: `testoConteggioVoci` prints
  "0 di 1" up to the cap and switches to "7 voci" beyond it, so the screen never
  prints an impossible ratio (`services/offer-request.js:176-179`, tested).
- **Agreement empty states name the lifecycle, not the emptiness**:
  "Quando invii una proposta, la trovi qui finché l'altra persona non risponde"
  (`agreements.jsx:38-40`).

Not specific — interchangeable with any CRUD app: the chrome bar and its
popover, the `Screen`/`PageHeader`/`Card`/`EmptyState`/`Banner` kit, the
filter-card → count-line → card-list → load-more catalog, and the whole staff
area. And the product's premise — **that nothing has a price** — is never said
on screen; grep for `gratuit|crediti|punti|moneta|euro` returns no UI copy. A
first-timer cannot distinguish "free by design" from "prices are somewhere
else". Nor does the composition admit pairwise exchange anywhere: an agreement
is a card in a list of three segments, never *one person gives / one receives*.

**Verdict:** character lives in the leaf components; the composition is
transferable. Swap in "services marketplace" copy and most pixels survive.

**Deterministic scan.** `impeccable detect --json Frontend/src` → `[]`, exit 0.
Zero findings, zero suppressions. That is consistent with what B measured by
hand: **0** hex/rgb literals outside `theme/tokens.js`, **0** inline
`borderRadius` numbers. The detector has nothing to catch here — every defect in
§3 is a *decision* problem, not a pattern problem.

**Browser overlay.** No live overlay was injected: the authenticated app cannot
be reached without the backend, and the two reachable routes are clean. The
browser was used instead for measurement (§7), which is what produced F16 and F6.

## 3. Findings

Severity: **P0** blocks a person, **P1** real friction on a main path or a rule
the project set for itself, **P2** polish with a visible cost. Finding ids are
stable — a future session should cite them, not renumber them.

### P0

None. Nothing in this tree stops a user from completing a task, and no data is
lost by any path inspected.

### P1

#### F1 — A logged-out visit to `/staff` or `/staff-users` is an unescapable fake load

**Evidence.** `logged-out-staff-deadend.png` — full-screen spinner, "Guardo le
segnalazioni…", no chrome, no message, no exit. Mechanism: `staff.jsx:71-75`
returns early when `token` is null, so `reports` stays `null`, and
`staff.jsx:190` then renders `<LoadingScreen>` forever. Identical shape at
`staff-users.jsx:98` → `:210`. The only auth redirect in the app lives in
`(tabs)/_layout.jsx:14`; `_layout.jsx:71-76` registers the four secondary routes
for any session and none of them guards itself.

**Why it matters.** A bookmarked or shared `/staff` URL, or a 401 during a
logout, leaves the person on a spinner that will never resolve, on a screen with
no navigation at all. It is the worst moment in the app and it looks like
patience, not failure.

**Smallest fix.** Branch on `!token` to the same `<Redirect href="/login">` the
tabs layout already uses. Two files, two lines. (`/edit-profile` has the same
missing guard but degrades differently — it renders an empty form whose save
fails; `/report` degrades correctly to its "missing params" state.)

#### F2 — The dialog is left-anchored instead of centred above 560 px

**Evidence.** `desktop-1280-navmenu-kb.png`: the service detail sheet sits at
x ≈ 16 with 704 px of dimmed overlay to its right, while the column it came from
is centred. `ModalShell.jsx:160-170` sets `justifyContent` (vertical) but never
`alignItems`, so the child — `width: '100%'`, `maxWidth: 560`
(`ModalShell.jsx:191-194`) — resolves to the start of the flex line. Invisible at
390 because the panel fills the width.

**Why it matters.** The detail sheet is the catalog's most-used surface and the
only place a proposal is sent. On a laptop it reads as a broken drawer, and it
does not sit over the card that opened it.

**Smallest fix.** `alignItems: 'center'` on the overlay container. The
bottom-aligned bell passes its own `contenitoreStyle` and already overrides it.

#### F3 — `PageHeader` is used by one screen out of ten, and the nine ad-hoc headers break two rules

**Evidence.** `PageHeader` is imported for a page title exactly once
(`(tabs)/index.jsx:240`). Nine routes hand-build the title row:
`agreements.jsx:205`, `offer-and-request.jsx:423`, `edit-profile.jsx:309`,
`staff.jsx:201`, `staff-users.jsx:224`, `register.jsx:340`, `match.jsx:17`,
`report.jsx:84`, `profile.jsx:221`. Two consequences, both visible:

1. **A second left edge on every back-navigable screen.** The row is
   `[BackButton 44pt][gap][title]`, so the H1 starts ~56 px right of the body
   column: title at x ≈ 420 against card at x ≈ 376 in
   `desktop-1280-edit-profile.png`; arrow at 36 against card at 20 in
   `mobile-390-report.png`. `DESIGN.md` § Measures warns about exactly this
   ("an element with a width of its own is how a screen ends up with several
   right edges") — here it is a left one.
2. **The subtitle slot carries usage instructions the written system forbids.**
   `PageHeader`'s own docstring: the second line says *what the screen holds*,
   never *how to use it*. `agreements.jsx:209-210` says "Le proposte ricevute si
   accettano o si rifiutano dalla campanella in basso a destra";
   `edit-profile.jsx:312-314` says where the fields go. That instruction belongs
   in the empty state that needs it.

**Why it matters.** This is the visible symptom of the whole consistency axis
(#4). It costs real scanning — the eye lands 40 px right of the column on four
screens — and it makes `DESIGN.md` describe a component the app does not use.

**Smallest fix.** Give `PageHeader` a `indietro` slot (the `azione` prop already
exists on the right and is used by nobody), migrate the nine call sites, and move
the bell instruction into the "Proposte inviate" empty state. The component's
`occhiello` and `azione` props are currently dead surface — either use them here
or delete them.

#### F4 — Three live regions are silent on web, including the app's only error surface

**Evidence.** `react-native-web` ignores `accessibilityLiveRegion` and reads only
`aria-live`. Three sites declare only the native one:

| Site | What goes unannounced on web |
| --- | --- |
| `Banner.jsx:40` | **every** error and success message on ten routes — `/`, `/agreements`, `/offer-and-request`, `/profile`, `/edit-profile`, `/report`, `/staff`, `/staff-users`, `/login`, `/register`, plus `SessionExpiryBanner` |
| `ServicesSection.jsx:88` | the result-count row ("20 di 197 servizi") |
| `staff-users.jsx:300` | the search-in-flight row |

Three other sites already declare both, with a comment explaining why
(`(tabs)/index.jsx:176-177`, `LoadingScreen.jsx:13-14`, `agreements.jsx:98-99`).
The app knows the rule and applies it in two of five places.

**Why it matters.** A screen-reader user who triggers an error on `/login` or a
failed proposal on `/` gets no announcement at all: the failure is silent until
they go looking for it. That is WCAG 4.1.3 (Status Messages).

**Smallest fix.** Add `aria-live="polite"` beside `accessibilityLiveRegion` at
the three sites. Better: one `LiveRegion` primitive, so the next one cannot be
half-declared.

#### F5 — The web chrome bar's controls are 40 pt tall, with no `hitSlop`

**Evidence.** `styles.controllo` sets `minHeight: 40` (`WebNavMenu.jsx:560`) and
is used by both the "Aggiorna" and the "Menu" control; `grep hitSlop
components/WebNavMenu.jsx` returns nothing. The comment defends 40 as "il minimo
utile dentro una barra da 48" — the bar is 48, so 44 fits.

**Why it matters.** The Menu button is the **only** navigation affordance on the
web target: every section switch on every screen goes through a 40 pt target.
`DESIGN.md` § Touch is unambiguous: `target.min` is the floor for every
pressable in both dimensions, and a control that cannot reach it is a defect, not
a density choice.

**Smallest fix.** `minHeight: 44`. One line.

#### F6 — The two auth links are 18 pt tall

**Evidence.** Measured live on the running web build:
`/login` → "Registrati" 59 × 18; `/register` → "Accedi" 40 × 18. Both are
`<Link asChild>` wrapping a bare `AppText variant="small"` (line-height 18):
`login.jsx:128-131`, `register.jsx:470-473`. This is the only pressable in the
app whose height is not declared.

**Why it matters.** On `/login` it is the only route to registration — a
first-timer's single exit from a screen they cannot pass — and it is a 18 pt
strip of text. `accessibility.md` § 2.5.5 sets 44.

**Smallest fix.** `minHeight: target.min` + `justifyContent: 'center'` on the
`AppText`, or wrap in a `Pressable`.

### P2

#### F7 — The retry is drawn two ways, and on `/profile` the retry becomes the screen's primary button

**Evidence.** Retry inside the message (`Banner` + `etichettaAzione`) on `/`
(`index.jsx:282-289`), `/agreements` (`:227-234`), `/staff` (`:213-220`),
`/report` (`:160-166`). Banner **plus a detached `AppButton`** on `/profile`
(`profile.jsx:166-170`), `/edit-profile` (`edit-profile.jsx:319-323`),
`/offer-and-request` (`offer-and-request.jsx:452-456`), `/staff-users`
(`staff-users.jsx:284-288`).

The sharp part: `profile.jsx:168` passes **no `variant`**, so the detached
"Riprova" is the *primary* (filled) variant — the strongest button on the screen
appears exactly when loading failed, competing with the profile content that
loaded before it.

**Smallest fix.** Pass `etichettaAzione="Riprova"` + `onAzione` to the existing
`Banner` at those four sites and delete the sibling buttons.

#### F8 — The dialog container receives the global focus ring

**Evidence.** `ModalShell.jsx:189` sets `tabIndex={-1}` and focuses the panel on
open (`:141`); `FocusRing.jsx:34` applies a global `:focus-visible` outline to
everything focusable. Result: a 2 px `primary` outline around the whole sheet, in
addition to its own primary button — visible in
`desktop-1280-navmenu-kb.png` and `mobile-390x667-service-detail.png`.

**Why it matters.** `DESIGN.md` colour rule 1: the accent is spent once per
screen. The sheet spends it twice and the ring reads as "the panel is selected".

**Smallest fix.** Exclude the dialog container from the ring (an
`outline: none` on the panel's own `focus-visible` state is enough; the panel is
a programmatic focus target, not a keyboard stop).

#### F9 — The accent is spent more than once per screen on three screens

**Evidence.** `DESIGN.md` colour rule 1: one filled `primary` element per screen,
plus data marks that classify.

| Screen | Accents visible |
| --- | --- |
| `/staff` (`desktop-1280-staff.png`) | filled "Tutte" pill **+** filled "Ricarica" button in the empty state |
| `/staff-users` (`desktop-1280-staff-users.png`) | filled "Tutti" pill ×2 **+** green "ATTIVO" chip |
| `/agreements` (`desktop-1280-agreements.png`) | filled segment "Invitate" **+** filled bell FAB |

**Smallest fix.** Pick one per screen. The segmented/track controls should mark
the active item with a tint (`serviceBg`) and bold text, as `ThemeSelector`
already does — that is the same "selected" state drawn two ways in one codebase.

#### F10 — The filter panel does not collapse after a choice is applied

**Evidence.** `FilterBar.jsx:81` owns `pannelloAperto`, `:135` toggles it only on
the summary row, and `applicaBozza` (`:88`) calls `onApplica` without touching
it. On 390 the expanded panel occupies the entire first viewport
(`mobile-390-filters-open.png`) and the results are below the fold **after every
selection**.

**Why it matters.** Filtering is a loop — pick, look, pick again. This design
makes every iteration cost a scroll down and a scroll back.

**Smallest fix.** Collapse on apply when the viewport is narrow, and keep it open
on wide screens where it costs one row.

#### F11 — The proposal-sent confirmation can land off-screen

**Evidence.** The success banner is part of the list header
(`(tabs)/index.jsx:238-253`, rendered as `ListHeaderComponent` at
`ServicesSection.jsx:85`), while the sheet can be opened from any row of a
20-row virtualised list. Code-path finding, not observed: the 2026-11-12 set has
no post-proposal capture.

**Why it matters.** Sending a blind proposal is the moment a user most needs the
system to answer. A confirmation they cannot see invites a duplicate send, which
the backend does not prevent (`index.jsx:66-71` documents duplicates).

**Smallest fix.** Render that banner in the same fixed chrome that already
carries "Aggiorna", or scroll the list to the header on success.

#### F12 — `/offer-and-request` says the same sentence twice, tells a desktop user to touch, and delivers a hard stop in the quietest voice

**Evidence.** `PublicationsSection.jsx:24-31` — `spiegazione` and
`vuoto.descrizione` both contain "con la categoria giusta gli altri ti trovano
nella home", 60 px apart. `:32` — "Tocca «Aggiungi» per pubblicarne una" on the
web build. At the demo's seven-voice state (`mobile-390-offer-and-request.png`)
the screen carries 21 same-weight buttons, and the blocking limit is 13 px grey
prose in the same voice as the section hint above it.

**Smallest fix.** One sentence per idea (drop the `spiegazione`, or fold it into
the empty state); "Seleziona" instead of "Tocca"; the limit becomes a `Banner`
with a real action rather than a paragraph.

#### F13 — `/staff` and `/staff-users` have no client-side role gate

**Evidence.** `_layout.jsx:71-76` registers both routes for **any** authenticated
user; only `/profile` hides the link (`profile.jsx:286`). A non-staff user who
types the URL gets the generic error banner after the 403.

**Smallest fix.** A role check beside the token check from F1, rendering a
distinct "questa sezione è riservata allo staff" state — the UI already hides the
link, so the route should agree with it.

#### F14 — There is no desktop composition; there is a phone column rendered wide

**Evidence (measured, both live and from captures).**

| Fact | Value |
| --- | --- |
| Widest content measure in the codebase | `layout.maxCatalogo = 720` (`tokens.js:131`, applied `Screen.jsx:81`) |
| Widest panel | 560 (`ModalShell.jsx:24`) |
| Catalog column at 1280 | ≈ 672 px of 1280, gutters ≈ 300 px each side |
| Catalog column at 1920 | ≈ 672 px of 1920, gutters ≈ 620 px each side (`desktop-1920-home.png`) |
| Login column at 1920 (live) | 560 px at x = 693 → **693 px of empty canvas on each side** |
| Distinct layout modes | **2** — the filter/confirm rows stack below 480 and go inline above it. Nothing else re-composes. |
| Surfaces using width ≥ 1024 | **none** |

Two side effects are visible in the captures: the "Aggiorna / Menu" bar floats
≈ 300 px away from the column's right edge in otherwise empty space, and the
**scroll thumb is drawn at the column's edge, not the window's** (≈ x 975 at
1280, ≈ x 1300 at 1920) because the scroll container is the column — so the
wheel over the gutters does nothing.

**Why it matters.** This is the weakest surface of the app and the one an
evaluator sees first on a laptop. It is not a taste problem: the frame is
literally a 390-wide design scaled to a 1920 canvas.

**Options, cheapest first.** (a) Move the scroll container to the page so the
scrollbar and the wheel behave normally — a real defect fix independent of
layout. (b) Accept the measure and use the gutters deliberately (the page header
and the trailing action already live outside it in `DESIGN.md`'s intent).
(c) A two-column measure at ≥ 1024. (a) is a fix; (b) and (c) are decisions that
belong in a direction doc, not in a polish pass.

#### F16 — `document.title` is empty on every route

**Evidence.** Measured live on `/login` and `/register`: `document.title === ""`,
`lang="it"` set. Every tab, bookmark and browser history entry reads as an
unnamed page.

**Smallest fix.** `expo-router`'s `Stack.Screen options.title` per route, or one
`useEffect` in `_layout.jsx` driven by the active route.

#### F17 — The two auth screens disagree on what the H1 is

**Evidence.** `/login` H1 = "Baratto-lo" (the wordmark, via
`AuthShell` `wordmarkAsTitle`); `/register` H1 = "Crea il tuo profilo" (the task,
`register.jsx:340`), with the wordmark demoted to `accessibilityRole="text"`.
Both are defensible; together they are a convention split. `/login` therefore has
no task heading at all — the word "Accedi" appears only inside the submit button.

**Smallest fix.** Pick one: the task is the H1 on both (the brand is already the
masthead's largest element), and `AuthShell` stops owning the title.

#### F18 — Two form fields on `/register` share the accessible name "Mansione"

**Evidence.** Measured live: the DOM exposes two `<textarea>` elements both named
"Mansione" (`AppInput.jsx:59` sets `accessibilityLabel={label}`, and
`EntryEditor` reuses the same label for the offer and the request).
`aria-describedby` and `aria-invalid` are wired correctly; the *name* is the
collision.

**Why it matters.** WCAG 3.3.2 (Labels or Instructions): a screen-reader user
filling the form is told "Mansione" twice with no way to know which is the offer
and which is the request.

**Smallest fix.** Pass a distinct `label` per section, or an
`accessibilityLabel` that names the section ("Mansione — cosa offri").

#### F19 — Dark theme: the scroll track is unthemed and surfaces barely separate

**Evidence.** `desktop-1280-home-dark.png`: a near-white scrollbar track runs the
full height at the column's right edge against `#111613` — the theme stops at the
content edge. Separately, `surface` `#1B221D` on `background` `#111613` is a
1.19:1 luminance step, so cards read as raised only through their 1 px border.

**Smallest fix.** The track is browser chrome: theming it needs
`scrollbar-color` (or `color-scheme: dark` on the root, which is the one-line
fix and also fixes form controls and the caret). The surface step is a token
decision for a direction doc, not a polish pass — the contrast audit says the
current values are *legible*, just flat.

## 4. What's working

1. **One card anatomy, and it is the product's anatomy.** `ServiceCard.jsx`
   puts the author's sentence in the headline role, folds
   category/mode/place/date/author into one 13 px strip, and makes the whole card
   one button whose accessible name carries the data (`:76`). Identical at 390
   and 1920, identical in both themes.
2. **Destructive actions are confirmed with the user's own text and a real exit.**
   Delete quotes the entry, names the recovery path ("la trovi in «Eliminati»")
   and the unaffected side-effects ("Gli accordi già avviati non cambiano")
   (`offer-and-request.jsx:101-111`); cancelling the staff review confirm
   restores the draft instead of discarding it (`staff.jsx:330-336`).

## 12. Questions this critique would change the design to answer

1. If a service is one person's sentence and every account holds exactly one
   offer and one request, what is *browsing* for? The home answers "what has been
   published"; the product's question is "who can swap with me" — and the tab
   that would answer it is a placeholder. The catalog is spending the entire
   composition budget on the side question.
2. The whole premise is that nothing has a price, and nothing on screen says so.
   If it were said once — masthead, empty catalog, or the sheet's footer, which
   already carries the blind-proposal line — what would the home stop needing to
   explain?
3. How often does anyone open "Offro e cerco" after the first week, given the
   ceiling is one entry per type? If the answer is "twice", why is it a full
   management dashboard with 21 buttons at the seven-voice state, instead of a
   setup step whose result is shown where people look?
