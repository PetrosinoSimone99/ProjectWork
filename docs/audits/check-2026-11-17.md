# Documentation and code audit — 2026-11-17

Read-only check of the whole documentation set against the code, with the
backend as the source of truth: the frontend must follow the backend **as
built**, and every document must describe what the repository actually does.

No file outside `docs/` was touched by this audit. The corrections it produced
are in the same commit as this report.

## Verdict on the frontend ↔ backend contract

**Clean.** All 33 calls the frontend makes match an existing route, method,
body and response. No invented field, no invented endpoint, no backend route
left unused by the app (`check-new-messages`, the one that looked unused, is
called by `api/areas/chat.js:getNewChatMessages`).

Spot-verified shapes: `{success:{code,message,agreements}}`,
`{chatId,messages}`, a bare array for `check-new-messages`, `{queues:[…]}` with
`serviceRemote` (the `ServiceQueueDTO` getter is `isServiceRemote`, so the wire
key is `serviceRemote` — `api/normalizers.js:normalizeQueue` reads exactly it),
`{notifications,pagination,unreadCount}`, `{profile}`, `{offers}`/`{requests}`,
`{service}` on `201`, `{user,offers,requests}`. Documented quirks are honoured:
`get-queues` `404` becomes `[]`, `cancel-queue` always answers `200`,
`send-message` returns no row, the sheet rows are looked up by username because
no participant id exists.

One residual risk, no action today: `isEndpointUnavailable()`
(`Frontend/src/api/client.js:70`) reads any `404` as "route missing". It is used
only by `StaffOperationsLog`. A legitimate `404` on a screen that used it would
render the wrong state.

## Security summary

The API authorisation probe of the same day
([`api-authz-2026-11-17.md`](api-authz-2026-11-17.md), A1–A6) already covered this
surface by making requests against the running stack. This audit confirms its two
main findings from the source and adds one thing the probe did not generalise:

1. **Chat authorisation (G24 = A1 + A2).** Any authenticated account can read the
   history of any agreement id and post into any chat id. The client cannot fix
   it: it only offers the chat from its own accepted agreements. Backend-only
   fix. Confirmed here in `ChatManager::getOrCreateChat:46` and
   `sendMessage:78`.
2. **Exception text in `5xx` bodies (G25, the general form of A3).** Five
   handlers append the exception message. Information leak; the UI never shows it
   (`ApiError.raw` is console-only), but it leaves the server.
3. **No login rate limit (G26 = A5).** Fifteen failures in a row cost nothing.
   No `rate_limiter` anywhere in `Backend/config/**`.
4. `POST /send-agreement-details` never calls `isParticipant` (A6), source-read
   only: a stranger reaching an accepted agreement gets a `500`, not a `404`.

Nothing else: the JWT is the only identity, no endpoint takes a user id from the
body, staff routes are gated by `^/api/staff → ROLE_STAFF`, and `^/api/categories`
is the only public route besides `/api/auth`.
