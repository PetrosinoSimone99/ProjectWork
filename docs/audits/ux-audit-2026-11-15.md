## 2. Findings

### P0 — the web build did not hydrate (fixed in this cycle)

`Frontend/src/app/+html.jsx` still rendered the pre-58 shape (`{children}` only).
Since Expo Router 58 the root HTML gets its bundle `<script>` tags **through
`useServerDocumentContext()` → `bodyNodes`**: without it the exported
`login.html` carried no script at all, the app stuck on "Preparazione di
Baratto-lo…" and **no web surface was usable** — measured with Playwright before
the fix (`document.body.innerText === "Preparazione di Baratto-lo…"`, one inline
script, zero bundle requests). Fixed in `cc6cf03`: the export now injects the
bundle and the rendered page reports `Accedi · Baratto-lo`.

### P1 — deleting a notification has no confirmation and is the loudest control

`NotificationRow.jsx` renders, per row, a `ghost` "Segna come letta" and a
`danger` "Elimina" (measured 120×50 and 187×50). The app confirms every other
irreversible action with `ConfirmModal` (`AgreementCard`, `report.jsx`), and here
a single tap destroys a row with no undo. Visually, the red outline is the
strongest thing on an otherwise calm card — a destructive action outshouting the
content (screens 02, 04).

**Smallest fix:** make the whole row the target for "open/expand", and put one
"Elimina" behind `ConfirmModal`; or keep two actions but move them into an
overflow menu, with the confirmation still there.

### P1 — the mini-card repeats the service you are already reading

Screenshot 05: the open service is "…ripasso di teoria musicale…", and the first
line under "Offre" is that same sentence again. Each row is a full 3-line
paragraph, so the card shows up to six paragraphs inside a modal that already
scrolls.

**Smallest fix:** pass the open service id and filter it out
(`UserServicesMiniCard` already receives `ownerId`; it needs `servizioId` too),
and give each row `numberOfLines={1}` — the full text lives on the service itself.

### P1 — unread is marked by a full green card fill

`NotificationRow.jsx:107-118` sets `backgroundColor: notifica.letta ? t.surface :
t.serviceBg` and a `t.primary` border. `DESIGN.md` reserves `serviceBg` for **data
marks** (category pill, published state, active nav row), not for a surface: with
fifteen unread rows the screen becomes a green wall, and the type chip
(`background: t.surface`) reads as a hole punched in the card (screens 02, 04).

**Smallest fix:** keep the card on `surface`, mark unread with the `primary`
border plus a leading dot or a bolder title, exactly like the agreements cards do.

### P2 — the polling sentence is said twice

The header `frase` says "Le notifiche arrivano quando riapri la schermata" and the
footer says the same thing again, longer (`notifications.jsx`). Keep the header
one, drop the footer; the empty state already explains what will arrive.

### P2 — the footer promises a gesture that does not exist

"…o tirando giù la lista viene chiesta l'ultima pagina." The screen is
`<Screen scroll>` without `refreshing`/`onRefresh`, so there is no pull-to-refresh
on either surface (`notifications.jsx:78`). Either wire the refresh (one line,
`useRefresh`) or delete the clause. Copy that promises an interaction is worse
than no copy.

### P2 — the count in the profile row is a bare digit

Screenshot 03: "Notifiche / 2 da leggere: proposte, risposte, schede e decisioni
della staff. **2** ›". The digit sits between the sentence and the chevron with
no container and repeats the number the sentence already says.
**Fix:** a `Chip` on `serviceBg` with "2" (or drop the digit and keep the
sentence).

### P2 — no "segna tutte come lette"

Twenty rows mean twenty taps. The API has no bulk route, so the honest version is
a client-side loop with a progress state — worth doing only if the inbox gets
used; recorded, not scheduled.

### P2 — mini-card rows look tappable and are not

They name a service without saying anything about it and cannot be opened. With
`numberOfLines={1}` and no affordance (no chevron, no underline) they read as
data, which is what they are; today they read as broken links.

### P3 — the inbox reloads only on focus

`useUnreadCount` and `useNotifications` both ask on focus. Coming back to a tab
that was already focused (web: same route, no remount) shows stale rows until a
reload. The copy says so, so this is documented behaviour, not a defect.

## 3. Technical checks (measured live)

| Check | Result |
| --- | --- |
| Headings | exactly one `H1` per screen ("Notifiche"); the empty state's title is a `generic`, not a second heading |
| Touch targets | smallest 44×44 (back arrow), menu 98×44, row buttons 50 tall — none under 44 pt |

| Contrast ratios | **not re-derived**: `tokens.js` was not touched this cycle, so the values audited on 2026-11-13 still hold. New pairs reuse existing tokens (`serviceBg`/`surface`, `primary`/`surface`, `danger`) |

**Environment note (not a design defect).** On the very first catalog request the
client aborted (`net::ERR_ABORTED`) because the cold PHP server exceeded the
10 s client timeout; a warm stack answers in under 1 s. Documented in
`docs/setup.md`; it is the same trap as before, not a regression.

## 5. What this critique did not verify

- Native rendering on iOS/Android (Expo Go 58.0.0): layout, safe areas, keyboard
  behaviour, and how the two-button row wraps on a 360 dp screen. Owed.
- The inbox with more than one page (`Carica altre`), and with an error after
  rows exist.
- The mini-card for an owner with **no** other services and for an inactive
  account: the code has those states, no data produced them.
- Dark theme. The captures are light only; `tokens.js` was unchanged, but the
  green card fill is the kind of change that reads very differently in dark.
- Contrast numbers (see §3).
- The `Elimina` flow end to end: the click was not exercised against the API.
